> 一句话本质：生产化 = `状态持久化` + `幂等重试` + `并发控制` + `超时熔断` + `灰度回滚`。

## 0. 先看问题

前 12 章我们一直在让 Agent **变聪明**：会调工具、会规划、会记忆、会反思、会协作。
但它们全都有一个共同的隐含假设 —— **进程一直活着，而且只服务我一个人。**

真实的线上环境里，这个假设会同时从四个方向被打破：

```
   你的本地机器                        真实的生产环境
 ┌────────────────┐            ┌──────────────────────────────────────┐
 │ 一个进程         │            │ 发布重启 / OOM Killer / Pod 被驱逐    │
 │ 一个请求         │            │ 用户双击 / 客户端自动重试 / 网关重发    │
 │ 你不刷新         │            │ 网关 30 秒就断开，你的任务要跑 90 秒   │
 │ 没有并发         │            │ 200 个并发一起抢模型连接              │
 └────────────────┘            └──────────────────────────────────────┘
        都能跑通                            全部出事
```

最典型的天真实现，几乎每个人第一次都是这么写的：

```python
agent = build_agent()                       # 状态在进程内存里
store = InMemoryCheckpointStore()           # "检查点"也在内存里

@app.post("/ask")
def ask(q: str):
    result = agent.run(q)                   # 一次请求 → 一次完整 run
    return {"answer": result.answer}        # 跑完才返回，中途断了就全没了
```

**它在本地永远是对的**，因为本地只有你一个人、一次请求、进程不会重启。

### 核心矛盾：大象与电话亭

```
┌──────────────────────────────────────────────────────────────────┐
│  Agent 的一次运行 = 有状态 + 长任务                                │
│      · 有状态：几十条消息的会话、已经调过的工具、已经花掉的钱        │
│      · 长任务：几十秒到几分钟、几十步、而且**带副作用**（扣款/发文） │
├──────────────────────────────────────────────────────────────────┤
│  HTTP 的一次请求 = 无状态 + 短连接                                 │
│      · 无状态：服务器不记得你上次请求过什么                          │
│      · 短连接：网关 3~30 秒就断了，断了就什么都没了                  │
└──────────────────────────────────────────────────────────────────┘
```

把长任务塞进短连接，就像把一头大象塞进电话亭 ——
**本地只有一头象时你能硬塞，上线后象群一来，电话亭就塌了。**

这一章要做的，就是给这头大象造一条**可持久化的轨道**：
让它在中途被打断时，既不丢工作、也不重复副作用。

## 1. 原理

### 1.1 状态持久化：把"活着"变成"存着"

关键认知：**Agent 的全部记忆就是那个 messages 列表**（第 01 章的第一课）。
所以持久化要存的东西非常少：

```
一次运行的全部状态
├─ messages          会话（Agent 的"记忆"，也是恢复的唯一依据）
├─ steps_done        已完成的步数（决定还剩几步预算）
├─ tool_hits         各工具已成功执行的次数（证明"没白跑、没重跑"）
└─ partial_answer    当前能拿得出手的半成品

存到哪里？
  教学：一个 JSON 文件（原子写）
  生产：Redis（快、带 TTL）/ Postgres（要事务、要查询）/ S3（要归档）
        —— 接口一模一样，换的是实现，不是逻辑
```

**必须原子写**。直接覆写有个致命窗口：

```
t0  打开文件（内容被截断）
t1  ← 此刻进程被杀：文件是空的 / 半截的
t2  写入新内容

结果：检查点变成一个坏 JSON。
      "崩溃恢复"于是退化成"崩溃 + 数据损坏"，比没有检查点更糟。

正确做法（所有数据库的通用套路）：
   写临时文件 → fsync 落盘 → os.replace() 原子改名
   要么全是旧内容，要么全是新内容，没有中间态。
```

### 1.2 检查点与续跑：恢复 = 倒回边界 + 重放

**检查点必须写在"步骤边界"上，不能写在"跑完"时** —— 跑完再存等于没存，
因为崩的那一刻恰恰是没跑完的时候。

```
 时间 ──────────────────────────────────────────────────────►
 步骤1        步骤2        步骤3        步骤4
   │            │            │            │
   ●────────────●────────────✗
   ↑            ↑            ↑
 存检查点      存检查点     进程在这里被 kill
                            （步骤 3 的一个"半成品"写操作自动作废，
                              因为恢复只看最后一个完整边界）

恢复流程：
  ① 新进程读检查点 → 拿到 [会话到步骤2] + steps_done=2
  ② 把会话**倒回"用户消息之前"**（关键！）
  ③ 交给 Agent.run() 重放 → 它会把用户消息重新追加一次 → 历史精确复原
  ④ 从"还剩几步"继续跑完
```

**为什么必须"倒回再重放"，而不是"接着中间状态写"？**

```
 ✗ 错误做法：恢复完整会话 → 再交给 Agent.run()
     Agent.run() 第一步永远是 conversation.add(Message.user(task))
     → 用户消息出现两次
     → 模型看到重复的问题，误判"什么都没做"
     → 从头再跑一遍
     → 最终答案看起来是对的，**工具调用却悄悄翻倍**
     （这正是幂等要防的事故本身）

 ✓ 正确做法：倒回"用户消息之前" → 重放
     Agent 追加的那条用户消息，恰好把历史补回原样
```

顺带一条同样重要的推论：**已完成动作只能从会话里推断，不能靠进程内存。**
生产里的 Worker 是**无状态**的，同一个请求可能被负载均衡打到任何一台机器上。
任何"跨请求残留的内存状态"，在大规模部署里都会变成一类诡异 bug。

### 1.3 幂等：重试时副作用不能发生第二次

```
用户点"支付" ──► 请求 A ──► 扣款 350 分 ✓
     │
     └── 网络抖动，没收到响应 ──► 客户端重试 ──► 请求 B ──► 扣款 350 分 ✗ 事故！
```

幂等的落点必须在**副作用那一层**，而不是在 API 层糊一层"看起来没报错"。

```
 ✗ 用 request_id 当幂等键
     客户端重试时几乎总会生成**新的** request_id
     → 等于没做幂等

 ✗ 用客户端给的 key 直接当全局缓存键
     幂等键是"命名空间内唯一"，不是"全局唯一"
     另一个用户碰巧也用了 "retry-1" → 错误命中缓存 → 钱记到别人头上
     → 必须拼上 (user_id, 业务意图) 才能当全局键

 ✓ 正确：幂等键由**掌握业务语义的那一层**生成，并在副作用层去重
     扣款/下单 → 客户端提供（只有它知道"这次算不算新的一次"）
     归档某订单/初始化某账号 → 服务端按业务主键推导（操作天然唯一）
```

三层纵深防御，一层都不能省：

```
   第 1 层  schema 校验     便宜、在入口，拦掉大部分脏参数
   第 2 层  函数内断言      拦住"长度够但语义是空"的垃圾键
   第 3 层  数据库唯一索引  ★ 并发下唯一真正可靠的一层
                           "先 SELECT 再 INSERT" 在并发下会双双通过检查
                           （check-then-act 竞态），只有唯一约束能兜住
```

还有一个容易被忽视的点：**幂等要幂等到"用户体验"那一层**。
如果工具第二次返回一个不一样的结果，模型就会对用户说"已为你扣款两次"——
**副作用没错，叙述错了，用户照样投诉。**
所以工具必须把 `replayed` 标记透传给模型。

### 1.4 并发控制：过载不是"慢"，是"死"

```
 没有上限时：
   200 并发 ──► 模型端 429（限流）──► 全部重试 ──► 更多请求 ──► 雪崩式超时
```

两种过载策略，选第二种：

```
 (A) 无限排队      延迟不可控地涨，用户等 3 分钟后超时，
                   白白占着连接 —— 排队把"过载"变成了"必然超时"

 (B) 快速拒绝 ★    返回 429 + Retry-After，诚实告诉对方"现在不行，0.5 秒后再试"
                   用户重试的成本，远低于挂死

 生产标准答案：短队列（吸收抖动）+ 队列满就拒绝（保护自己）
```

闸门必须放在**调模型之前** —— 因为每个 run 都占着一条模型连接 + 一份内存。

### 1.5 超时与降级：给半成品，而不是挂死

超时的正确姿势是"**在干净的步骤边界上收手**"，而不是"跑到一半硬砍"。

```
   钉在两个时刻：
     step_start  → 每步开始前检查（别一开始就来不及）
     llm_output  → ★ 模型刚回来、工具还没执行时检查
                   这一条保证绝不会出现"已经超时了，却又发了一条通知"

   超时后的返回（三件套，缺一不可）：
     ✓ 部分结果      已经拿到的信息，别浪费
     ✓ 明确说明      已完成几步、卡在哪、为什么停
     ✓ 可续跑标记    检查点还在，给个 run_id 就能接着跑
```

对比两种失败方式：

```
 ✗ 挂死：连接一直占着 → 网关 30 秒后断开 → 用户看到 504
        而你的进程还在傻跑 —— 算力白烧，用户还不知道进度
 ✓ 降级：2 秒返回半成品 + "已完成 2/3 步，可续跑"
        用户能决策（要不要等 / 要不要重试），你也没有浪费算力
```

**熔断器**：下游已经躺了，就别再打它。三个状态是所有熔断器的标准形状：

```
  CLOSED   ──连续失败 ≥ 阈值──►  OPEN
    ▲                             │
    │                       冷却时间到
 探测成功                        │
    └──── HALF_OPEN ◄────────────┘
          只放**一个**探测请求：
          成了→恢复；不成→重新计时
          （放一批的话，下游还没好就被你二次打死 —— 熔断抖动）
```

熔断的价值是**阻断故障扩散**：下游躺了，你还每个请求去敲它、等它超时，
只会把上游的线程/连接池一起拖死，最后整条链路一起挂。

### 1.6 结构化日志：回答"是哪一次运行的哪一步失败了"

生产事故的第一个问题永远是这句话。自由文本日志答不了（只能人肉 grep + 猜）。

```json
{"ts": 31.23, "run_id": "run-777", "step": 1, "event": "run_failed",
 "ms": 0.0, "level": "error", "reason": "error",
 "error": "LLM 连续失败 1 次: 模型服务 503"}
```

```
 字段     回答什么问题
 ──────── ──────────────────────────────────────────────────────
 ts       还原时序：是"先超时"还是"先报错"？顺序不同，根因不同
 run_id   ★ 全链路关联键。所有事件 + 所有下游调用都用它串起来（OTel trace_id）
 step     定位"卡在第几步"——降级说明、重试决策都要用它
 event    机器可聚合：error 占比、checkpoint_saved 频率、各步耗时 p99
 ms       性能回归的第一手证据（模型变慢了？工具变慢了？）
 level    告警路由：warn 进周报，error 直接叫人
 extra    上下文：工具名、错误类型、路由决策、灰度版本
```

### 1.7 灰度发布与自动回滚

**为什么 Agent 特别需要灰度？** 因为它的输出是**概率性**的。
传统服务改代码，单测能覆盖 90%；Agent 改了提示词、换了模型，
你**没法靠单测证明它没变坏**。
离线靠评估集（第 10 章），在线靠灰度（本章），两者是一对。

```
 流量 ──► 路由器 ──┬── 60% ──► stable 版本
                   └── 40% ──► canary 版本（新提示词 / 新模型 / 新工具）
                                  │
                            实时统计错误率、延迟
                                  │
                     窗口错误率 > 阈值？ ──► ★ 自动回滚（开关级，秒级生效）
```

路由必须按**稳定键哈希**，不能用 `random()`：

```python
bucket = int(sha256(request_id)[:8], 16) % 100
version = "canary" if bucket < rollout_percent else "stable"
```

```
 ✗ random()       用户刷新一下就被分到另一个版本，答案突然变了；
                  同一个 request 在多台机器上落点不同，灰度比例变成一锅粥
 ✗ 内置 hash()    带随机盐（PYTHONHASHSEED），跨进程不稳定
 ✓ sha256         跨进程、跨机器都稳定 —— 灰度实验的数据才可信
```

两个容易被写错的护栏：

```
 min_samples   样本太少时比例没有统计意义（1 个请求失败 = 100% 错误率）
               样本不足就别急着回滚
 滑动窗口      ★ 用"最近 N 次"的错误率，不要用总错误率
               总错误率会被"上线前的健康历史"稀释，
               你会眼睁睁看着它从 0.1% 慢慢爬，等它超阈值时已经烧了一片
```

### 2.1 运行时：五道闸门串成一条管道

```python
class ProductionRuntime:
    def submit(self, req: Request) -> RunResponse:
        # 闸门 ①：幂等（最便宜，放最前面）
        ck = IdempotencyCache.cache_key(req.idempotency_key, req.user_id, req.task)
        hit = self.cache.get(ck)
        if hit is not None:
            return RunResponse(answer=hit["answer"], reason="idempotent_replay",
                               cached=True, replayed=True)

        # 闸门 ②：熔断（下游已经挂了就别再打它）
        if not self.breaker.allow():
            return RunResponse(reason="circuit_open", rejected=True,
                               retry_after_s=self.breaker.retry_after())

        # 闸门 ③：并发准入（满了就快速拒绝，不排队）
        if not self.limiter.try_acquire():
            return RunResponse(reason="overloaded", rejected=True,
                               retry_after_s=self.limiter.retry_after_s)

        # 闸门 ④：执行（可续跑引擎）  ⑤：记录（日志 + 指标）
        try:
            return self._publish(req)
        finally:
            self.limiter.release()
```

**设计决定：所有闸门都在"执行之前"，且都不依赖模型。**
生产事故里最忌讳"用模型来判断要不要调用模型"——准入、去重、熔断必须是纯确定性的代码
（第 09 章的同一句话：能用确定性代码解决的，绝不用模型）。

**设计决定：`submit()` 永远不把异常抛给调用方。**
任何一步的失败都有明确的返回结构 —— 抛出去就等于用户看到 500、而你什么都不知道。

### 2.2 检查点：钉在步骤边界上

```python
def observer(event, payload):
    if event == "step_start":
        budget.check(about_to=f"第 {step} 步的模型调用", signal=_BudgetSignal)
    if event == "llm_output":
        # ★ 模型刚回来、工具还没执行 —— 停在这里就绝不会"超时了还发通知"
        budget.check(about_to=f"第 {step} 步的工具执行", signal=_BudgetSignal)
        return
    if event not in {"tool_result", "final_answer"}:
        return
    # 用"做了哪几步"的**列表**记账，而不是累加计数器
    completed.append({"step": ..., "kind": ..., "tool": ..., "ok": ...})
    state.steps_done = len(completed)
    state.set_conversation(conv)
    state.completed_steps = [dict(c) for c in completed]
    self.store.save(state)                # ← 每一步之后落盘
```

**为什么记账用"列表"而不是"计数器"？**
因为一旦进程中途死过、续跑过，
`逻辑步号 = 之前步数 + 本次步数` 这种推导极容易算重。
而"把每一步的名字追加进一个列表"天然幂等：死多少次都只是补几条。

> 一般化的工程建议：**状态尽量存"事实清单"，而不是"累计数字"。**
> 累计数字一旦重复计算就无法自愈，事实清单可以随时重新求值。

**为什么要 `signal=_BudgetSignal`？** 因为踩了两个真实的坑：

```python
# 坑 1：core/agent.py 的 _emit() 有一句
try:
    self.observer(event, payload)
except Exception:
    pass                    # ← 观察者崩了不能拖垮主流程

# 坑 2：core/agent.py 的 run() 最外层还有
except AgentError as exc:
    stop_reason = "error"   # ← BudgetExceeded 正是 AgentError 的子类！

# 后果：我们精心抛出的"崩溃"和"超时"被兜底逻辑**静默吃掉**，
#       实验看起来跑完了、其实根本没崩；用户看到的不是"超时降级"而是"跑挂了"。
```

解法：让"中断"走一条 `except Exception` 抓不到的通道 ——
`SimulatedCrash` 和 `_BudgetSignal` 都继承 `BaseException`
（和 `KeyboardInterrupt` / `SystemExit` 同一类）。

> 这条经验在生产里叫 **"不要把中断混进错误体系"**：
> 超时、取消、关机信号应该走独立通道，
> 否则它们迟早会被某个"兜底错误处理"吞掉，表现成"偶发地不生效"。

### 2.3 超时降级：半成品 + 说明

```python
if outcome.stop_reason == "timeout":
    state.state = STATUS_CRASHED          # 可续跑：检查点仍在
    self.store.save(state)
    return RunResponse(
        answer=outcome.answer, reason="timeout", degraded=True,
        extra={"partial_answer": state.partial_answer,
               "explain": f"任务超出时间预算已停止（已完成 {state.steps_done} 步）；"
                          f"检查点已保留，可用 run_id 续跑",
               "resumable": True},
    )
```

注意 `_finalize` 里的一句关键设计：**只有 `final_answer` 才写幂等缓存。**
绝不能提前写 —— 提前写会把"失败"缓存成"成功"，
用户重试时拿到一个假成功，**比重复执行更糟**。

### 2.4 虚拟时钟：让"超时"可测

```python
class FakeClock:
    """可以手动推进的假时钟 —— 只在教学与测试里用。"""
    def __call__(self) -> float:
        return self._now
    def advance(self, seconds: float) -> float:
        self._now += float(seconds)
        return self._now
```

运行时只调用 `clock()` 拿当前时间，**从不直接读系统时间**。
测试时换掉它，"30 秒熔断冷却"就压缩成"推进 30 秒"——
测试瞬间完成、而且永远稳定。

这不是教学玩具：Java 的 `java.time.Clock`、Go 的 `clockwork`、
Python 的 `freezegun` 都是同一个思路。**你这 20 行就是它们的原理。**

### 2.6 灰度路由

def bucket(self, request_id: str) -> int:

    return int(digest[:8], 16) % 100        # sha256：跨进程稳定

def _maybe_rollback(self) -> None:

### 观察点 3：幂等的三道防线（第 ③ 节）

```
  ▶ 同一个幂等键，分两次提交（第 2 次模拟「用户重试 / 网络重发」）

    实际扣款            : 1 次

  ▶ 如果换一个**不同**的幂等键呢？（用户是真的想再充一次）
  ℹ️    所以这里换一个**全新的运行时**（新的账本 = 新的「外部世界」）——

    实际扣款            : 2 次 / 700 分
  ℹ️  这正是幂等键的正确语义：**它区分的是「业务意图」，不是「请求次数」。**
  ℹ️  给幂等键设计一个稳定的推导规则（用户+业务+业务主键），比随手 uuid4() 重要得多。
  ℹ️  真实支付系统还会再加一层「业务级去重」（同一用户+同一金额+短时间窗内只收一次），

## 4. 工程要点

### 上线前的生产检查清单

| # | 检查项 | 不做的后果 | 本章对应 |
|---|---|---|---|
| 1 | Agent 状态落在**进程之外**的存储里 | 发布重启 = 用户任务全丢 | `CheckpointStore` / `FileCheckpointStore` |
| 2 | 检查点写在**步骤边界**上，且**原子写** | 崩溃后拿到坏 JSON，恢复变事故 | `observer` / `os.replace` |
| 3 | 恢复走"**倒回起点 + 重放**" | 用户消息重复，工具被重跑 | `CheckpointedEngine.start` |
| 4 | 有副作用的操作**必带幂等键** | 重复扣款、重复发通知 | `charge_user` / `SideEffectLedger` |
| 5 | 幂等键**作用域**正确（拼 user_id + 业务意图） | 不同用户互相命中缓存 | `IdempotencyCache.cache_key` |
| 6 | 幂等键**跨进程稳定**（sha256，不用内置 hash） | 重启后幂等失效 | `fingerprint()` |
| 7 | 副作用层有**唯一约束**兜底 | 并发下 check-then-act 竞态 | 账本（真实里是 DB 唯一索引） |
| 8 | 有**并发上限**，满了快速拒绝 | 过载雪崩，全体超时 | `OverloadGuard` |
| 9 | 有**墙钟预算**，超时降级返回半成品 | 挂死到网关超时，算力白烧 | `Budget` / `status=timeout` |
| 10 | 超时检查点在**步骤边界**（工具执行前） | "超时了却还发了通知" | `llm_output` 处 check |
| 11 | 下游故障有**熔断**，不全量重试 | 故障扩散，整条链路一起挂 | `CircuitBreaker` |
| 12 | 日志**结构化**、带 run_id 与 step | 排障靠猜，事故复盘做不出来 | `EventLog` |
| 13 | 灰度按**稳定哈希**路由，有**自动回滚** | 坏版本全量上线，或用户答案跳变 | `CanaryRouter` |
| 14 | 超时/取消走**独立中断通道** | 被兜底 except 吞掉，偶发不生效 | `SimulatedCrash` / `_BudgetSignal` |
| 15 | 失败**不写**幂等缓存 | 用户重试拿到假成功 | `_finalize` 只在成功后 put |

### 常见坑（都是本章真的踩过的）

```
 1. 用"空值"表达"未设置"
    `if not state.messages_before: 记录起点` —— 首次运行的起点本来就是空会话，
    空值是合法取值，判据直接失效。该用独立的 bool 标记。

 2. 同一个语义字段有多个写入点
    "起点会话"被崩溃处理顺手覆盖成"跑了一半的状态"，
    恢复时用户消息被追加两次 → 模型从头再跑 → 工具调用悄悄翻倍。
    **一个语义一个写入点**，多写入点 + 无保护 = 迟早写错。

 3. 用"累计数字"表达状态
    `steps_done` 中途死过再续跑时极容易算重（1 → 3 → 6 → 10）。
    改成"事实清单"（做了哪几步的列表）后天然幂等。

 4. 兜底 except 吃掉中断信号
    `except Exception: pass` 和 `except AgentError` 会把你自己抛的
    "崩溃/超时"翻译成普通错误。中断必须走 BaseException 通道。

 5. Python 闭包捕获的是"变量"而不是"值"
    `for rid in ids: lambda: build(request_id=rid)` 会全部拿到最后一个 rid，
    反例实验静默失效（本该重复扣款的场景"碰巧"变幂等了）。
    用默认参数或工厂函数绑定。

 6. 用 request_id / 内置 hash() 当幂等键
    前者客户端一换就失效；后者带随机盐，跨进程不稳定。

 7. 用总错误率做灰度决策
    会被历史健康数据稀释，等它超阈值时已经烧了一片 —— 要用滑动窗口。
```

### 映射到真实部署

| 本章手写的 | 真实生产里的形态 |
|---|---|
| `FileCheckpointStore` | Redis（`SET run:{id} <json> EX 3600`）/ Postgres `agent_runs` 表 / S3 归档 |
| 同步 `submit()` | **队列 + Worker**：API 只入队并返回 `run_id`，Worker 池消费（Celery / SQS / Kafka） |
| 进程内的 `OverloadGuard` | 网关限流（Nginx `limit_req`）+ 服务端并发信号量 + K8s HPA 扩容 |
| `InMemoryCheckpointStore` 的教训 | **不要用本地磁盘**存检查点：Pod 是无状态的，下次调度可能落到另一台机器 |
| `EventLog` | OpenTelemetry：`run_id` 当 trace_id，Agent 的每一步是一个 span，工具调用是子 span |
| `IdempotencyCache` | Redis `SETNX` + 数据库唯一索引（两层都要） |
| `CanaryRouter` | Feature Flag 服务（LaunchDarkly / 自研）+ Ingress 权重路由 + 指标驱动的自动回滚 |
| `Metrics` | Prometheus 计数器 + Grafana 看板 + 告警规则 |
| 幂等键 | HTTP `Idempotency-Key` 头（Stripe / 支付宝的开放 API 都有这个约定） |

                              │
                        ┌─────▼─────┐
                        │  队列      │  Redis Stream / SQS / Kafka
                        └─────┬─────┘
                              │  多个 Worker 并发消费（每个都无状态、可随时被杀）
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
          Worker 1        Worker 2        Worker 3
              │               │               │
              └───────────────┴───────────────┘

                              ▼
                    状态存储（Redis / Postgres）

  GET /agent/tasks/{run_id}  ──►  查询状态与结果（长轮询 / SSE / WebSocket 推进度）
  POST /agent/tasks/{run_id}/resume  ──►  手动续跑（补偿任务也调它）
```

**注意这里的关键转变**：HTTP 请求不再"跑完才返回"，而是"入队就返回"。
于是"长任务"和"短连接"的矛盾的**根本解法**是 ——
**不要让 HTTP 连接去承载任务的生命周期**。

## 5. 练习

### 练习 1（基础）：把检查点换成内存版，观察会发生什么

把 `demo_checkpoint_resume` 里的 `FileCheckpointStore` 换成 `InMemoryCheckpointStore`，
然后跑 `--section 2`。

**提示**：崩溃发生时，那个 `InMemoryCheckpointStore` 对象**还在**（因为我们没真杀进程），
所以你会发现"恢复"居然是成功的。请想清楚：
**这个实验为什么没有复现真实故障？** 真实场景里丢掉的到底是什么？
（答案：丢掉的是"进程"本身 —— `store` 和 `agent` 都在那个进程里。
教学里的"假崩溃"只抛异常不销毁对象，所以内存版看起来能扛。
真实上线时它一秒都扛不住。请把 `simulate_restart()` 也加进恢复流程，
或者干脆新建一个 `InMemoryCheckpointStore`，看恢复还能不能成立。）

### 练习 2（基础）：给幂等键加 TTL

`IdempotencyCache` 现在只有容量上限（LRU），没有过期时间。

1. 给它加 `ttl_s` 参数和基于 `time.time()` 的惰性过期（读的时候判断）；
2. 用 `FakeClock` 写一个自检：**TTL 内命中缓存、TTL 外重新执行**；
3. 想一想：TTL 设长了会怎样（用户第二天真的想再充一次，却被当成重复）？
   设短了又会怎样？

**提示**：真实系统的 TTL 是按**业务**定的，不是按技术定的。
支付类通常 24 小时，点赞类可能 5 分钟。

### 练习 3（进阶）：把"超时"改成"每步超时"

现在的 `Budget` 只有**整轮**的墙钟预算。真实系统往往还需要**单步**超时
（某一次模型调用卡住 60 秒，也该被砍掉，而不是吃掉整轮预算）。

1. 给 `Budget` 加 `step_seconds`；
2. 在 `CheckpointedEngine` 的 `llm_output` 检查点里，同时判断单步耗时；
3. 设计一个自检：一步正常、一步超长，验证只有超长那步被砍。

**提示**：单步超时和整轮超时是不同的失败语义：
整轮超时 → 返回半成品；单步超时 → 应该**重试这一步**（换一次调用），而不是整轮降级。

### 练习 4（进阶）：给熔断器加"半开只放一个"的保证

现在的 `HALF_OPEN` 状态下 `allow()` 永远返回 `True`，
如果同时来了 10 个请求，就会有 10 个探测请求打过去 —— 这正是我们注释里
说要避免的"熔断抖动"。

1. 加一个 `_probe_in_flight: bool`，让 `HALF_OPEN` 只放**一个**请求；
2. 探测请求结束后（成功或失败）必须复位这个标志，否则熔断器会永远卡住
   （这叫**状态机卡死**，是熔断器最常见的实现 bug）；
3. 写自检证明：`HALF_OPEN` 下连续 5 次 `allow()` 只有 1 次返回 `True`。

### 练习 5（破坏性实验，必做）：拆掉守卫，看它怎么坏

本章每一个守卫都请你**亲手拆掉一次**，观察后果。这是最快建立直觉的方式：

| 拆掉什么 | 怎么拆 | 预期看到什么 |
|---|---|---|
| 幂等闸门 | `submit()` 里注释掉 `cache.get(ck)` 那段 | 同一个键提交两次 → 实际扣款 2 次 |
| 幂等的作用域 | `cache_key()` 改成直接 `return idempotency_key` | 换 `user_id` 但仍命中缓存 → 钱记到别人头上 |
| 检查点的原子写 | `save()` 改成直接 `open(path,"w").write(...)` | 单进程看不出来；把写入拆成两步就能看到半截 JSON |
| 恢复时的"倒回" | 删掉 `start()` 里 `conv.messages.pop()` 那一行 | 用户消息出现两次，`lookup_order` 被重跑（计数从 1 变 2） |
| 超时的 `llm_output` 检查 | 注释掉那行 `budget.check(...)` | 超时后仍然会执行第 3 步的工具 —— 会产生不该发生的副作用 |
| 熔断器 | `allow()` 永远 `return True` | 每次请求都去敲已经挂掉的下游，`short_circuited` 恒为 0 |
| 灰度的稳定哈希 | `bucket()` 改成 `random.randint(0, 99)` | 同一个 request_id 每次落不同版本；连查 3 次结果不一致 |

**做完请回答**：哪一处的"坏"最不容易被发现？
（提示：想想"恢复时用户消息重复"那一行 —— 最终答案是对的、日志是正常的、
检查点也在，**只有工具调用计数悄悄翻倍**。静默的错误远比崩溃危险。）

## 7. 全课程回顾

### 13 章各自给"生产化"贡献了什么

| 章 | 主题 | 它对最终生产架构的贡献 |
|---|---|---|
| 01 | 最小 Agent 循环 | `while` 循环 + `StepRecord` 轨迹 —— 后来所有检查点的**写入时机**都基于它 |
| 02 | 工具系统与 JSON Schema | 工具成了可校验、可注册的对象 —— 幂等键与权限才能挂在"工具"这个边界上 |
| 03 | ReAct 提示工程 | 输出格式契约 —— 它让"模型输出"可解析，于是"步骤"才能被可靠地计数 |
| 04 | 规划与任务分解 | 计划是假设、执行是验证 —— 续跑时"还剩哪几步"就来自这里 |
| 05 | 记忆与上下文工程 | 记忆分层与压缩 —— 检查点里该存什么、能丢什么，由它决定 |
| 06 | RAG 检索增强 | 外部知识注入 —— 生产上它是独立的检索服务，也要熔断、也要降级 |
| 07 | 反思与自我修正 | 失败经验库 —— 它就是"跨 run 的持久状态"，同样需要幂等写入 |
| 08 | 多智能体协作 | 角色分工与消息传递 —— 多 Agent 让"状态"变成了分布式问题 |
| 09 | 工作流与状态机 | 显式图 + 节点检查点 —— 本章的 `RunState` 状态机直接沿用它的思想 |
| 10 | 评估与可观测性 | 评估集 + trace —— 离线评估管"改动前 vs 改动后"，在线灰度管真实流量 |
| 11 | 安全护栏 | 输入过滤 + 审批 + 审计 —— 高危操作的人工审批必须**跨进程持久化**，否则重启即失效 |
| 12 | 成本与延迟优化 | 计量、缓存、路由 —— 成本指标要进监控看板，缓存命中率是容量规划的依据 |
| 13 | **生产化部署** | **把前 12 章的全部机制，装进一个"坏了也不出事"的服务外壳里** |

### 三句话总结整门课

```
 第一句（第 01 章）：
     Agent = 一个 while 循环 + 一个会调工具的模型 + 一个能记住历史的列表。

 第二句（第 02~12 章）：
     让它变聪明，靠的不是"更强的模型"，
     而是更好的工具描述、更清晰的提示词契约、更严格的校验、更完整的评估。

 第三句（第 13 章）：
     让它敢上线，靠的不是"更多的功能"，
     而是状态持久化、幂等、并发控制、超时熔断、灰度回滚
     —— 一句话：**在坏掉的时候也不出事。**
```

### 最后回到那个核心矛盾

```
   Agent 是有状态的长任务，HTTP 是无状态的短连接。

   第 01~12 章，我们一直在把"长任务"这一半做得更强；
   第 13 章，我们补上了另外一半：
       用检查点把状态从进程里搬出来，
       用幂等让重试变得安全，
       用准入和熔断把过载挡在门外，
       用降级和回滚承认"系统一定会坏"。

   成熟的工程不是"不会坏"，
   而是"坏了以后，用户几乎感觉不到，而你知道发生了什么"。
```

> **一句话本质**：生产化 = `状态持久化` + `幂等重试` + `并发控制` + `超时熔断` + `灰度回滚`。
> 核心矛盾是：**Agent 是有状态的长任务，而 HTTP 是无状态短连接**。
