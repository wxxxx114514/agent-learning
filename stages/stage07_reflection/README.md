## 0. 先看问题

第 06 章之前，我们的 Agent 已经能查资料、能调工具、能多步推理。但它有一个致命的盲区：

**它错了，它自己不知道。**

让模型写一份销售速报（三个商品的小计 + 一个合计），它交出来的是这样：

```
2025 年 Q1 销售速报
分项：
- A 商品：17 件 × 23 元 = 391 元
- B 商品：8 件 × 45 元 = 360 元
- C 商品：5 件 × 12 元 = 60 元
合计：801 元                      ← 391+360+60 = 811，少了 10 元
结论：本季度销售整体稳健，建议优先补货 A 商品。
```

三个分项全对，**合计错了 10 元**。而模型对自己的产出非常自信 —— 它不会说"我可能算错了"。

这时候新手的第一反应是加一句提示词：

```python
"请你再仔细检查一遍上面的内容，确认无误后再输出。"
```

跑一下，你会得到：

```
整体结构清晰、逻辑通顺、语言表达自然，建议进一步打磨细节，确保数据准确、结论更有深度，表述更加凝练。
```

**合计还是 801。** 这段"自评"一个字都没改，还吃掉了一次模型调用。

问题出在哪？本章要回答三件事：

1. 为什么"自己检查自己"几乎总是无效？
2. 什么样的反馈能让模型真的改？（答案：位置 + 事实 + 动作）
3. 改到什么时候停？（答案：验证器说通过，或者轮数用完）

## 1. 原理

### 1.1 为什么"自评"不可靠

自评和生成用的是**同一个模型、同一套先验**。它算错的地方，它同样看不出来 —— 这就是
`self-consistency bias`。指望它"再想一遍就想对了"，等于指望同一个人用同样的思路得出不同结论。

真正的解法是把"检查"换成一个**不同的问题**：

| | 生成 | 自评 | 验证（verifier） |
|---|---|---|---|
| 问题 | 写一份速报 | 你觉得写得怎么样？ | 391+360+60 等于几？ |
| 依据 | 语言能力 | 语言能力（同一套） | 事实源（明细表 / 规则） |
| 结论 | 文本 | "整体不错" | 是 / 否，可复现 |
| 成本 | 1 次调用 | 1 次调用 | **0 次调用** |
| 可靠 | 会错 | 会放水 | 100% 确定 |

**只要"对错"能被代码判定，就应该交给代码判。** 算术、格式、JSON schema、SQL 结果、
必填字段、引用编号 —— 这些都轮不到模型来"感觉"。

### 1.2 一条有效的反馈长什么样

```
┌─────────────────────────────────────────────────────────────┐
│  笼统反馈（无效）              │  具体反馈（有效）            │
├────────────────────────────────┼─────────────────────────────┤
│  "建议进一步打磨细节，          │  "第 5 行「合计」有误：      │
│   确保数据准确"                 │   391 + 360 + 60 = 811，     │
│                                │   你写成了 801；             │
│  ← 无位置、无事实、无动作       │   请把 801 改成 811。"       │
│  → 模型只能改措辞               │  ← 位置 + 事实 + 动作        │
│                                │  → 模型能精确执行            │
└─────────────────────────────────────────────────────────────┘
```

三要素缺一不可：

- **位置**：哪一行 / 哪个字段 / 哪个函数（否则模型不知道该动哪里）
- **事实**：正确值是多少，依据是什么（否则模型只能猜）
- **动作**：把 X 改成 Y（否则模型不知道要干什么）

### 1.3 Reflexion 循环

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
   │ 生成     │───▶│ 审查      │───▶│ 合成反馈  │───▶│ 修正      │
   │ (LLM)   │    │ critic   │    │ verifier │    │ (LLM)    │
   └─────────┘    │ (LLM)    │    │ +critic  │    └──────────┘
                  └──────────┘    └──────────┘
                       │                │
                       ▼                ▼
                  ┌─────────────────────────────┐
                  │ 停机判定（三道刹车）          │
                  │  ① verifier 通过 + 无意见 → 交付
                  │  ② 事实错误一字未改     → no_progress
                  │  ③ 到达 max_rounds      → 强制停机
                  └─────────────────────────────┘
```

三条停机路径对应三种现实：

| 停机原因 | 含义 | 交付时该怎么做 |
|---|---|---|
| `verified_pass` | 事实正确、审查者无异议 | 正常交付 |
| `no_progress` | 反馈没被采纳，再跑也是白跑 | 交付 + 告警（反馈质量问题） |
| `max_rounds` | 审查者永不满意 | 交付 + **标注未闭环的异议** |

### 1.4 反思的收益要靠"经验库"兑现

反思改对的是**这一次**。要把收益留存下来，必须把教训写成结构化条目，下一次同类任务开工前注入提示词：

```
这一次错 ──▶ Lesson(kind, mistake, fix, source) ──▶ 下一次开工时注入 ──▶ 不再犯
```

**只改这一次的反思是昂贵的补丁；能让下一次不犯的反思才是资产。**

## 2. 动手实现

代码在 `stages/stage07_reflection/demo.py`。全部离线：三个"确定性假模型"精确复现了真实模型的
行为规律（对具体反馈敏感、对笼统反馈免疫），所以这条因果链你可以跑一百遍，结论都一样。

### 2.1 事实源：反思的前提

```python
@dataclass(frozen=True)
class ReportTask:
    key: str                      # 任务编号，用于经验库溯源
    kind: str                     # 任务类型，经验库按类型复用
    title: str
    records: tuple[SalesRecord, ...]

    def correct_total(self) -> int:
        return sum(r.subtotal for r in self.records)

    def wrong_total(self) -> int:
        """假模型"心算"出来的错误合计：少算 10 元（模拟真实的漏进位）。"""
        return self.correct_total() - 10
```

**设计决定**：事实源用 `frozen=True` 的 dataclass。反思过程中它绝不能被改写 ——
如果"正确答案"会随对话漂移，验证器就失去意义了。

### 2.2 验证器：6 行代码替代一次模型调用

```python
class ReportVerifier:
    """确定性验证器：重算每一个数字，校验格式契约。一次模型调用都不需要。"""

    def check(self, text: str, task: ReportTask) -> Verdict:
        issues, checked = [], []
        for r in task.records:                                    # ① 逐项重算
            want = f"{r.qty} 件 × {r.price} 元 = {r.subtotal} 元"
            checked.append(f"分项 {r.sku}：数量 × 单价 = {r.subtotal}")
            if want not in text:
                issues.append(f"分项「{r.sku}」缺失或金额不等于 {r.subtotal} 元")
        total = task.correct_total()                              # ② 合计 = 逐项之和
        m = re.search(r"合计[:：]\s*(\d+)\s*元", text)
        if not m:
            issues.append(f"缺少「合计：{total} 元」这一行")
        elif int(m.group(1)) != total:
            got = int(m.group(1))
            issues.append(f"合计错误：逐项重算应为 {total}，你写成了 {got}；请把 {got} 改成 {total}")
        if "结论：" not in text:                                  # ③ 格式契约
            issues.append("缺少「结论：」段落，交付格式不合规")
        return Verdict(ok=not issues, issues=issues, checked=checked)
```

两个细节值得学：

1. **`checked` 字段**：验证器必须能说清"我到底检查了什么"。这是审计和回归测试的抓手。
2. **错误信息里带正确值**：`请把 801 改成 811` —— 验证器的输出**直接就是一条可执行的反馈**。
   这是最省钱的用法：不用再花钱请一个"审查者模型"。

### 2.3 主循环：把刹车写进结构里

```python
for i in range(1, self.max_rounds + 1):
    if feedback:
        messages.append(Message.user(feedback))
    draft = self.llm.complete(messages).text          # ① 生成 / 修正
    messages.append(Message.assistant(draft))

    verdict  = self.verifier.check(draft, task)       # ② 事实层（0 次调用）
    critique = self.critic.review(draft, task)        # ③ 语言层（1 次调用）

    key = tuple(verdict.issues)
    rounds.append(Round(i, draft, critique, verdict, feedback))

    if verdict.ok and not critique.blocking:          # 刹车 ①：真的好了
        stop_reason = "verified_pass"; break
    if key and key == last_issue_key:                 # 刹车 ②：原地踏步
        stop_reason = "no_progress"; break
    last_issue_key = key
    feedback = build_feedback(critique, verdict, self.use_verifier_feedback)
```

**`use_verifier_feedback` 这个开关是刻意留的**：关掉它做实验，就能把"审查者的话"这一个变量单独拎出来，
看清笼统批评和具体修正的差距（第 ② 节）。

### 2.4 反馈合成：事实优先于意见

```python
def build_feedback(critique, verdict, use_verifier_feedback=True) -> str:
    lines = []
    if use_verifier_feedback:
        lines += [f"- [验证器] {i}" for i in verdict.issues]     # 事实排最前
    lines += [f"- [审查者] {i}" for i in critique.actionable]    # 只保留可执行条目
    if not lines:
        return ""
    return "【修正意见】请逐条落实（只改被指出的地方，不要重写全文）：\n" + "\n".join(lines)
```

为什么要过滤掉"不可执行条目"？因为笼统建议对模型是**噪声**：它会挤占上下文、稀释真正的修改点，
还会让模型以为"我改过了"。

## 4. 工程要点

**① 反思的第一个瓶颈是"有没有事实源"，不是"提示词写得好不好"。**
本章的验证器之所以 6 行就能写完，是因为"合计 = 逐项之和"是确定的。真实业务里，
你的第一步应该是问："这件事的对错，谁能判定？" —— 找得到一个可执行的判据，反思才有意义；
找不到，就需要人（第 09 章的人工介入节点）。

**② 永远不要用模型做它能被代码判定的事。**
合规检查、金额一致性、必填字段、引用编号、JSON 合法性 —— 这些一旦交给模型，
你就得到了一个"这次说行、下次说不行"的系统。**合规要求每次判断都一样。**

**③ 反思的成本是 N 倍，必须设上限。**
一次反思 = 至少 2 次模型调用（审查 + 重写）。本章的默认值是 `max_rounds=3`：
第一轮生成 + 最多两轮反思。真实项目里这个值通常是 1~3，再高就要先问"是不是验证器不够强"。

**④ 停机必须分类，不能只有一个 `failed`。**
`verified_pass` / `no_progress` / `max_rounds` 三种停机的**运维动作完全不同**：
- `no_progress` → 反馈管道有问题（审查者在说废话，或者反馈没送进模型）
- `max_rounds` → 目标不可满足（审查者的标准是主观的、无法收敛的）
把它们混成一个失败，你就永远定位不到问题。

**⑤ 未闭环的异议要交给用户，不要假装完美。**
`ReflexionResult.unresolved` 就是干这个的。生产系统里它应该出现在工单备注、UI 提示、
或者日志的 WARN 级别里。

**⑥ 经验库要有类型（kind）和溯源（source）。**
不分类的经验库 = 往上下文里倒垃圾（第 05 章的教训）；不可溯源的教训，人不敢信也不敢删。

**⑦ 常见误区速查**

| 误区 | 现实 |
|---|---|
| "让它自己再检查一遍" | 自评会放水，必须给事实依据 |
| "反思轮数越多越好" | 成本 N 倍，且主观标准下永不收敛 |
| "把整段对话都塞给审查者" | 上下文越长越容易走神，只给草稿 + 事实源 |
| "教训记下来就行了" | 必须在下一次**开工前注入提示词**，否则等于没记 |
| "验证器太麻烦，用模型判吧" | 一次模型调用的钱，换一个不确定的裁判 —— 不划算 |

## 5. 练习

**练习 1（必做）：把刹车拆掉，观察会发生什么。**
把 `demo.py` 里 `ReflexionAgent` 的 `max_rounds` 改成 `50`，用 `mode="nitpick"` 的审查者跑一次，
观察 `len(result.rounds)` 和 `result.llm_calls`。
*提示*：你会得到 50 轮 —— 每一轮都是一次真实的模型调用。再想想：如果这是线上系统，
一个"永远不满意"的审查者会花掉你多少钱？这也解释了为什么 `max_rounds` 不是可选项。

**练习 2：让验证器更严。**
给 `ReportVerifier` 加一条检查：结论段里提到的商品必须出现在分项里（防止模型在结论里编一个"补货 D 商品"）。
*提示*：在 `check()` 里加第 ④ 条规则，然后构造一个"合计对但结论编了商品"的草稿做反向验证。
别忘了在 `run_checks()` 里补一条对应的检查项。

**练习 3：给"经验库"加上失效机制。**
现在的 `LessonMemory` 只增不减。如果一条教训被后续 3 次同类任务证明"已经不再出错"，
就应该降低它的优先级（或者归档）。
*提示*：给 `Lesson` 加 `hits` / `success_streak` 字段，`as_prompt()` 里按 `success_streak` 过滤。
想想为什么这和"记忆遗忘策略"（第 05 章）是同一个问题。

**练习 4：把笼统批评"翻译"成具体修正。**
新增一个 `RepairPlanner`：它接收笼统的审查意见 + 事实源，输出可执行的修正条目
（其实就是本章"具体派审查者"干的事），然后接在笼统派审查者后面。
*提示*：这就是工业界的 `critique → actionable plan` 两步走。跑一遍对照实验，看笼统派 +
翻译器的效果能不能追平具体派，代价是几次调用。

**练习 5：换一个真实模型试试（可选）。**
把 `make_agent()` 里的 `ReportWriterLLM` 换成 `core.real_llm.get_llm()`（需要 API Key），
把 `--real` 参数接上。你会观察到两件事：
① 真实模型第一次**未必**算错（它可能直接给出 811）；
② 但它一旦算错，笼统的"再检查一遍"依然救不回来。
这说明本章的结构与模型强弱无关 —— **反思是架构问题，不是模型问题**。
