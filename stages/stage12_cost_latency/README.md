## 0. 先看问题

第 11 章结束时，你的 Agent 已经能安全上线了。然后账单来了。

先用**真 Agent**（`core/agent.py`）跑一次任务，把每一次调用都记下来（第 ① 节真实输出）：

```
  #  档位   模型       输入  输出  耗时    TTFT   成本      备注
  -  -----  ---------  ----  ----  ------  -----  --------  ----
  1  large  mock-rule  778   48    2200ms  700ms  ¥0.01106
  2  large  mock-rule  828   31    2200ms  700ms  ¥0.01105

  答案                : 根据 calc 的结果：(12+8)*3/4 = 15
  LLM 调用次数          : 2
  输入 / 输出 token     : 1606 / 79
  本次成本              : ¥0.02212

  - 一次任务几分钱听起来不多，但乘上量级就是决策问题：
  每天 1000 次任务       : ¥22.12/天 ≈ ¥663.48/月
```

两个立刻能看出来的事实：

1. **输入 token 是逐次累加的**（778 → 828）：每调一次模型都要把整段历史重发一遍。
   这就是"上下文越长越贵"的根源 —— 第 05 章的上下文管理，直接决定这里的账单。
2. **成本是可以算出来的**：有了单价和 token 数，"贵不贵"就不再是感觉。

而大多数团队的真实反应是："换个便宜的小模型吧。"
这是最差的起手式：它直接牺牲质量，而且**治不了"本可以不发生的调用"**。

## 1. 原理

### 1.1 优化顺序（本章的主线）

```
   ① 测量          ② 缓存          ③ 减量          ④ 路由/换模型
 ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
 │ 成本可计算│ → │ 重复问题  │ → │ 并行/裁剪 │ → │ 简单给小  │
 │ 延迟可归因│   │ 0 次调用  │   │ /流式     │   │ 复杂给大  │
 └──────────┘   └──────────┘   └──────────┘   └──────────┘
   不动质量       不动质量       不动质量      ★ 直接动质量
```

为什么顺序不能反？

| 顺序 | 收益 | 风险 |
|---|---|---|
| 先换小模型 | 成本立刻降 | **质量立刻降**，且你不知道降了多少 |
| 先缓存 | 成本降、延迟降 | 几乎为零（只要防住假命中） |
| 先减量 | 延迟降、输入 token 降 | 需要判断工具依赖关系 |
| 最后路由 | 成本再降一个台阶 | 需要评估集兜住质量 |

### 1.2 四个零件

| 零件 | 解决什么 | 关键指标 |
|---|---|---|
| `UsageMeter` | 成本/延迟可计算 | token in/out、成本、墙上时间、TTFT |
| `SemanticCache` | 重复调用 | 命中率、**假命中率**（必须为 0） |
| 并行/裁剪/流式 | 延迟与输入 token | sum→max、窗口内 token 数、TTFT |
| `ModelRouter` | 用对模型 | 路由准确率（靠评估集验证） |

### 1.3 缓存的两个闸门

```
   新问题 ──→ 归一化 key ──完全一致？──→ 精确命中（最安全）
                 │ 否
                 ▼
            相似度 ≥ 阈值？ ──否──→ 未命中（走真调用）
                 │ 是
                 ▼
            实体集合一致？ ──否──→ ★ 拒绝命中（这就是"假命中"防线）
                 │ 是
                 ▼
              语义命中
```

**假命中**是缓存唯一真正危险的失败模式：它不会报错、不会变慢，
只会**把 A 的信息答给问 B 的用户**。本章的第 ③ 节用一对只差一个字符的订单号
（`A1001` / `A1002`，相似度 0.78）现场演示了这件事。

### 1.4 延迟的两个不同指标

| 指标 | 含义 | 优化手段 |
|---|---|---|
| 总时长（wall time） | 从提问到答案完整呈现 | 并行工具、缓存、小模型 |
| **TTFT**（首字延迟） | 从提问到**第一个字**出现 | 流式输出 |

流式**不省任何成本**，总时长也不变，但它把"用户对着空白屏幕等 2.2 秒"
变成"0.7 秒后开始持续出字"。用户感知的"快"主要来自 TTFT。

## 2. 动手实现

### 2.1 计量器：所有成本计算的唯一真相来源

```python
@dataclass(frozen=True)
class Price:
    name: str
    prompt_per_1k: float       # 输入单价
    completion_per_1k: float   # 输出单价
    sim_latency_ms: float
    sim_ttft_ms: float

    def cost(self, prompt_tokens: int, completion_tokens: int) -> float:
        return (prompt_tokens / 1000 * self.prompt_per_1k
                + completion_tokens / 1000 * self.completion_per_1k)
```

三个必须记住的单位陷阱：

1. 各家报价都是"每 **100 万** token" —— 换算成"每 1K"要除以 1000，**别少乘一个零**；
2. 输入和输出**不同价**（输出通常是输入的 3~5 倍，所以啰嗦的回答更贵）；
3. 缓存命中、批处理、夜间折扣是不同档位，价目表要能表达它们。

记账发生在**最靠近模型调用的那一层**：

```python
class MeteredLLM(LLM):
    def _complete(self, messages, **kwargs):
        resp = self.inner.complete(messages, **kwargs)
        price = self.meter.pricing[self.tier]
        latency = float(resp.raw.get("sim_latency_ms") or price.sim_latency_ms)
        self.meter.record_call(tier=self.tier, prompt_tokens=..., completion_tokens=...,
                               latency_ms=latency, ttft_ms=..., model=self.inner.model)
        return resp
```

> 为什么不能"在业务代码里顺手加一下"？因为业务代码一定会漏。
> 生产里这一层就是你的 LLM 网关 —— 它是所有调用的必经之路。

### 2.2 缓存：归一化 + 相似度 + 实体硬约束

```python
def _norm(text: str) -> str:
    t = (text or "").strip().lower()
    t = re.sub(r"[，。！？、；：,.!?;:~\"'“”‘’()（）\[\]【】]", "", t)   # 去标点
    t = re.sub(r"(帮我|请|麻烦|一下|一下子|谢谢|好吗|可以|能不能|我想|我要)", "", t)  # 去礼貌词
    return re.sub(r"\s+", "", t)

ENTITY_RE = re.compile(r"[A-Za-z]{0,2}\d{2,}")     # 订单号、编号
NUMBER_RE = re.compile(r"\d+(?:\.\d+)?")           # 金额、日期、数量

def similarity(a: str, b: str) -> float:
    """Dice 相似度：2|A∩B| / (|A|+|B|)，A/B 是字符二元组集合。"""
    ga, gb = bigrams(a), bigrams(b)
    return 2 * len(ga & gb) / (len(ga) + len(gb)) if ga and gb else 0.0
```

为什么用字符二元组而不是 embedding？因为本章要**零依赖、可解释、可复现**。
生产里可以换成 embedding + 向量库，但下面这层不能省：

```python
if entry is not None and score >= self.threshold:
    if self.entity_guard and entry.entities != ents:
        self.stats["entity_blocked"] += 1
        return CacheLookup(False, "entity_blocked", entry, score,
                           f"相似度 {score:.2f} 达标，但实体不同 … → 拒绝命中")
```

`entity_guard=False` 时会发生什么，demo 里跑给你看：

```
  关掉实体约束后           : semantic 命中 → 问「订单 A1002 到哪了？」，答「订单 A1001 已发货，承运商顺丰。」
```

### 2.3 路由：默认走大模型

```python
def route(self, question: str) -> RouteDecision:
    q = question.strip()
    if len(q) > self.long_char_threshold:
        return RouteDecision("large", f"长度 {len(q)} 字符 > 阈值，信息量大")
    if any(h in q for h in COMPLEX_HINTS):        # 分析/对比/为什么/设计…
        return RouteDecision("large", "命中复杂意图词")
    if any(h in q for h in SIMPLE_HINTS):         # 计算/统计/查询/翻译…
        return RouteDecision("small", "命中简单意图词")
    return RouteDecision("large", "无法判断 → 保守走大模型")   # ★ 兜底
```

兜底为什么是大模型？因为**路由错误的代价不对称**：

- 简单问题给大模型 → 多花一点钱（可控）；
- 复杂问题给小模型 → 用户拿到烂答案（不可控，而且会流失）。

demo 里那句对比值得抄进笔记：

```
    │ 大模型：从订单 A1001 的物流节点看，延迟主要来自中转仓积压（占比约 60%）；建议：① …
    │ 小模型：订单延迟了，建议尽快联系快递。
```

小模型的回答"没错"，但它没有可执行信息。**这种退化无法用"正确率"衡量**，
只能用第 10 章的评估集 + 评判发现。

### 2.4 并行、裁剪、流式

```python
def run_tools_sequential(calls):        # 总耗时 = sum
    return ..., sum(c.sim_ms for c in calls)

def run_tools_parallel(calls):          # 总耗时 ≈ max
    with ThreadPoolExecutor(max_workers=len(calls)) as pool:
        futures = [pool.submit(lambda c=c: f"{c.name}:ok") for c in calls]
        out = [f.result() for f in futures]
    return out, max((c.sim_ms for c in calls), default=0.0)
```

判断能不能并行的标准很简单：**B 的参数里有没有用到 A 的返回值？** 没有 → 可以并行。

关于延迟的诚实说明：假模型真实耗时接近 0，没法演示延迟优化，所以模型会
**声明**一个模拟耗时（`sim_latency_ms`）。真实项目里这些数字就是实测值，口径一样。

### 2.5 预算兜底：优化降低期望值，预算控制上界

```python
class BudgetGuard:
    def check(self, meter: UsageMeter) -> None:
        if meter.model_calls >= self.max_calls:
            raise BudgetExceeded(f"调用次数预算耗尽：{meter.model_calls}/{self.max_calls}")
        if meter.cost >= self.max_cost:
            raise BudgetExceeded(...)
        if meter.wall_ms >= self.max_wall_ms:
            raise BudgetExceeded(...)
```

`BudgetExceeded` 在 `core/errors.py` 里已经是 `AbortAgent` 的子类 ——
它是**预期内的策略性停机**，不是故障，所以应该优雅地返回已完成的部分，
而不是当成 500 错误去告警。检查必须放在**调用之前**：放在之后只是事后统计，拦不住账单。

## 4. 工程要点

**1）先量化，再动手。**
"感觉有点慢"不是需求，"P95 首字延迟 2.2 秒、月成本 ¥663"才是需求。
没有基线的优化无法验收，也无法复盘。

**2）优化的优先级：能省一次调用 > 能省一点 token > 能换个小模型。**
一次调用的成本是"整个上下文 + 输出"，省 token 只能省边际，换模型动的是质量。

**3）缓存的 key 设计比相似度算法重要 100 倍。**
必须进 key 的东西：用户/租户 ID（**绝不能跨用户共享缓存！**）、权限级别、
工具集版本、模型版本、知识库版本、语言。少一个就是数据泄露或答非所问。

**4）语义缓存的阈值要用真实流量调，不能拍脑袋。**
做法：先只记日志不生效（shadow mode），人工看 200 组"被判定为相似"的样本，
统计假命中率。**假命中率必须为 0**，命中率低没关系（还有 100% 的精确命中兜着）。

**5）把"缓存命中率"当成一等指标。**
它同时影响成本、延迟和用户体验。命中率突然掉了，通常是上游改了措辞或
你的 `_norm()` 改坏了 —— 这两个都是事故级信号。

**6）并行不是万能的。**
有依赖的工具必须串行；并行还会带来限流（上游 QPS 限制）、资源争抢、
部分失败的处理（一个成功一个超时怎么办）。先确认工具真的无依赖。

**7）prompt 前缀缓存（prefix caching）值得单独关注。**
很多厂商对"相同前缀"的输入 token 打折（甚至打 1 折）。把**稳定的内容放前面**
（系统提示词、工具说明、长期记忆），把**变化的内容放后面**（用户输入、检索结果），
就能吃到这部分折扣。这是一个不改一行逻辑就能省钱的优化。

**8）成本优化最大的敌人不是单价，是"没必要的调用"。**
常见的浪费来源：每轮都重发全部历史、把没用到的工具说明塞进提示词、
多智能体互相转发消息、失败后无上限重试、循环检测不严导致的空转。

**9）常见坑速查**

| 坑 | 现象 | 解药 |
|---|---|---|
| 单位算错 | 成本差 1000 倍 | 统一用"每 1K token"当内部单位 |
| 跨用户共享缓存 | 数据泄露（严重事故） | key 里必须带租户/用户 ID |
| 语义缓存假命中 | A 的信息答给 B | 实体硬约束 + 假命中率监控 |
| 缓存旧数据 | 用户信息过期 | 带 TTL + 写操作后主动失效 |
| 路由过激 | 复杂问题掉质量 | 兜底走大模型 + 评估集验证 |
| 预算检查滞后 | 账单失控 | 调用前检查；三维度（次数/金额/时间） |
| 只看平均延迟 | P99 用户已流失 | 看 P50/P95/P99 和 TTFT |

## 5. 练习

**练习 1（必做）：打破缓存护栏，观察会发生什么。**
把第 ③ 节里的 `SemanticCache(threshold=0.72)` 改成 `threshold=0.5`，重跑 `--section 3`。
预期：更多问题会命中语义缓存。**再加一句 `"订单 A1003 到哪了？"` 并观察 `entity_blocked`
是否兜住了它**。然后做最危险的一步：把 `entity_guard=False` 也打开，看假命中是怎么产生的。

**练习 2（必做）：让成本算错一次。**
把 `Price.cost()` 里的 `prompt_tokens / 1000` 改成 `prompt_tokens / 100`，重跑 `--check`。
预期：`成本计算与手算一致` 这一条立刻变红。**这就是"计量器必须可验证"的意义**——
线上的价目表改错了，是不会有任何报错的，只会悄悄多扣钱。

**练习 3：给路由加一条规则，并用评估集验证它。**
现在的 `SIMPLE_HINTS` 里没有"总结"。加一条把"总结一下这段文字"路由到 small 的规则，
然后跑 `--section 4` 观察。接着思考：你凭什么说这条规则是安全的？
（提示：用第 10 章的做法，为它准备 10 条评估用例，对比大小模型的回答质量。）

**练习 4：把流式输出的 TTFT 收益算成钱。**
假设"用户等待超过 1 秒就流失 5%"，每天 1000 次任务。
算出把 TTFT 从 2200ms 降到 700ms 能挽回多少用户。
提示：这属于**体验收益**，要和成本收益放在同一张 ROI 表里 —— 优化才有优先级。

**练习 5（进阶）：实现 TTL 与写失效。**
给 `SemanticCache` 加一个 `ttl_ms` 参数，以及在写操作（如第 11 章的 `write_note`）
成功后调用 `cache.invalidate_entities(entities)`。
提示：先想清楚"哪些缓存必须失效"（任何被写操作影响到的实体），
再想"过期时长设多少"（业务能容忍多旧的数据）。
