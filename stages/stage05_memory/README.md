## 0. 先看问题

第 04 章的 Planner-Executor 会产出大量中间结果：每一版计划、每一步的观测、每一次重规划的原因。
第 01 章的 `messages` 列表则会把它们**全部**留在一个不断增长的数组里。

我们用一个 50 轮的对话把这个麻烦放大（`--section 1` 的真实输出）：

```text
  ℹ️  对话共 50 轮。关键事实全在**最前面 4 轮**（真实对话就是这样）：
  - 第 1 轮：你好，我叫张三，我在筹备下个月的部门团建。
  - 第 2 轮：我们一共 24 人，预算 5000 元，日期定在 3 月 15 日。
  - 第 3 轮：重要提醒：我对海鲜过敏，餐厅一定要避开海鲜。
  - 第 4 轮：另外订单 A1001 的发票麻烦一起处理。

  方案 A · 全量历史       : 102 条消息 / 2691 token
      [##############################]  2691/1200 token (100%)
  ⚠️  超出预算 2.2 倍。真实 API 到这里会直接报错（上下文超限）

  方案 B · 只留最近 6 轮   : 14 条消息 / 372 token
      [#########.....................]   372/1200 token ( 31%)

  Agent 的回答         : 我在当前上下文里只能确认：（什么都没有）。
以下信息在上下文里找不到：姓名、饮食禁忌、预算、订单号。
```

两个朴素方案，恰好死在两个极端：

| 方案 | 预算 | 效果 | 死因 |
|---|---|---|---|
| A 全量塞进去 | **爆**（2.2 倍） | 好 | 上下文有硬上限；而且每轮重发全部历史，成本随轮数平方级增长 |
| B 只留最近 N 轮 | 省 | **关键事实全丢** | **按时间淘汰 = 按无关性淘汰** |

B 的危险不在于"忘事"，而在于**忘掉的是最要命的那条**：

- 第 1 轮说的「我对海鲜过敏」比第 46 轮说的「桌游道具」重要得多；
- 真实事故：上下文里没有过敏信息 → 模型推荐了含花生的餐厅 → 这是**幻觉之外**的一类事故，
  根因是**上下文供给不足**，而不是模型能力不足；
- 更隐蔽的是：它不报错。Agent 会很自信地把"你叫什么我没印象"当成正常回答。

## 1. 原理

### 1.1 三个层次的记忆

```
┌──────────────────────────────────────────────────────────────────────┐
│  短期记忆（消息窗口）   最近 N 轮原文，细节最全，只覆盖最近几轮         │
├──────────────────────────────────────────────────────────────────────┤
│  工作记忆（当前任务）   这一版计划、已完成步骤的结果、失败原因（第 04 章）│
├──────────────────────────────────────────────────────────────────────┤
│  长期记忆（外部存储）   事实库 / 用户画像 / 向量库，跨会话存在，按需检索  │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.2 四件套，缺一不可

| 机制 | 覆盖范围 | 保真度 | 致命弱点 |
|---|---|---|---|
| 滑动窗口 | 最近几轮 | 原文，100% | 覆盖太短，早期的关键信息看不到 |
| 摘要压缩 | 全部历史 | 有损，会悄悄漏 | 一定漏；且"摘要的摘要"会衰减 |
| 事实钉住 | 关键事实 | 精确 | 必须有上限，否则自己变成超支来源 |
| 长期存储 | 跨会话 | 精确 | 检索不准时，注入的是**污染**而不是帮助 |

它们不是"四选一"，而是**四层纵深防御**：摘要漏掉的靠钉住兜，钉住装不下的靠存储兜。
本章 `--section 4` 会把这三层一层层拆掉，让你看到每一层都在承重。

### 1.3 预算分配顺序 = 策略

```
① 系统提示   不可压缩（压缩它等于改程序）
② 钉住事实   硬上限 MAX_PINNED=8，按重要性排序
③ 长期召回   必须过相关性闸门（宁可少注入，不可乱注入）
④ 滚动摘要   有字数上限，是"更早的对话"的唯一代表
⑤ 对话窗口   拿走剩下的全部（最新的原文）
⑥ 当前问题   永远放最后
```

排序依据是**不可替代性**：系统提示不可替代，最新一轮也不可替代（它带着当前问题）。

### 1.4 位置也是信息（Lost in the Middle）

```
   ┌─────────────────────────────┐
   │ 系统提示 + 钉住事实          │ ← 注意力高 ✓
   │ ...                         │
   │ 大段大段的参考资料           │ ← 注意力低 ✗（内容再好也可能被忽略）
   │ ...                         │
   │ 最近几轮对话 + 当前问题      │ ← 注意力高 ✓
   └─────────────────────────────┘
```

研究结论（Liu et al., 2023）：模型对上下文**开头和结尾**的利用显著优于中间。
所以本章把"钉住事实"放在最前面、"当前问题"放在最后面 —— 这不是排版偏好，是**性能优化**。

### 1.5 淘汰策略：按价值，不按时间

```python
# ✗ 按时间淘汰：最早的最先死（而最早说的往往是最关键的约束）
messages = messages[-20:]

# ✓ 按价值淘汰：先抽事实 → 打分 → 钉住高价值的 → 再压缩其余
facts = extract(messages)                      # 结构化的"记下的事"
pinned = [f for f in facts if f.importance >= 0.75][:MAX_PINNED]
summary = compress(aged_turns)                 # 其余压成摘要
```

## 2. 动手实现

`memory.py` 有 6 部分，照着这个顺序读最省力：

```
meter / Section   →  算账（预算表）
Fact / FactExtractor  →  什么值得记
RuleSummarizer   →  摘要压缩
LongTermStore    →  长期存储与检索
Turn / ContextPack / MemoryManager  →  组装
full_history / naive_truncate  →  对照组（没有它们，你没法证明自己变好了）
```

### 2.1 算账先于压缩（`Section` / `meter`）

```python
def meter(used: int, total: int, width: int = 30) -> str:
    ratio = min(used / total, 1.0) if total else 0.0
    filled = int(round(width * ratio))
    return f"[{'#' * filled}{'.' * (width - filled)}] {used:>5}/{total} token ({ratio * 100:>3.0f}%)"
```

`ContextPack.sections` 是一本**账**：每一块花了多少 token、为什么存在、上限是多少。
账本自洽（分块之和 == 实际总量）是自检项之一 —— **账算不清，就一定管不住**。

### 2.2 事实抽取：什么值得钉住

```python
FACT_RULES = [
    (r"我叫([\u4e00-\u9fa5A-Za-z]{2,4})", "姓名", 1.00),
    (r"我(?:对|吃)?([\u4e00-\u9fa5]{2,6})过敏", "饮食禁忌", 1.00),
    (r"预算(?:是|为|大概)?\s*([0-9,]+)\s*(?:元|块|万)", "预算", 0.98),
    ...
]
PIN_THRESHOLD = 0.75      # 重要性阈值
MAX_PINNED = 8            # ★ 钉住区也必须有上限
```

判断标准只有一条：**这条信息后面还会不会被用到？用错了会不会出事？**

`MAX_PINNED` 那一行是重点：钉住区如果没有上限，它就变成了一个新的、不可压缩的超支来源 ——
**"永不淘汰"的机制必须自带配额**，这是所有缓存/记忆系统的通例。

### 2.3 滚动摘要：增量，而不是每次重算

```python
def _compress_if_needed(self) -> None:
    aged = self.turns[: len(self.turns) - self.window_turns]
    if len(aged) <= self.compressed_turns:
        return
    new_pieces = [t.user + "。" + t.assistant for t in aged[self.compressed_turns:]]
    pieces = ([self.summary_text] if self.summary_text else []) + new_pieces   # ★ 旧摘要参与
    self.summary_text = self.summarizer.summarize(pieces)
    self.compressed_turns = len(aged)
```

两个细节决定成败：

1. **旧摘要参与下一轮压缩** —— 否则"很久以前的事"会在反复重算里一点点漂移消失；
2. **摘要必须有字数上限** —— 摘要自己无限膨胀的话，压缩就白做了。

生产环境里摘要是让模型写的（提示词见 `memory.py` 的 `SUMMARY_PROMPT`），
但要注意：**摘要本身也是一次模型调用，也要花钱、也有延迟**。

### 2.4 长期记忆：写入 + 检索 + 闸门

```python
def bigrams(text: str) -> set[str]:
    clean = re.sub(r"\s+", "", text or "")
    return {clean[i:i + 2] for i in range(len(clean) - 1)} or ({clean} if clean else set())

def search(self, query, top_k=3, min_score=1.0):
    q = bigrams(query)
    scored = [(len(q & bigrams(it.text)) + it.importance, it) for it in self.items
              if len(q & bigrams(it.text)) >= min_score]
    ...
```

- 中文按**字符二元组**切分，零依赖、无需分词库，关键词级召回足够好；
- `min_score` 是**闸门**：不相关就不注入。注入无关记忆比不注入更糟 ——
  模型会把旧任务的约束当成当前任务的约束（上次 24 人，这次 6 人也按 24 人办）；
- 二元组检索**不懂同义词**：查询「忌口」召不回记忆「饮食禁忌：海鲜」。
  这是本章实测出来的局限，也正是第 06 章要用向量检索解决的问题。

### 2.5 组装：顺序就是策略

```python
pack.messages.append(Message.system(self.system_prompt))      # ① 系统提示
pack.messages.append(Message.system(pinned_text))             # ② 钉住事实（最前！）
pack.messages.append(Message.system(recall_text))             # ③ 长期召回
pack.messages.append(Message.system(summary_text))            # ④ 滚动摘要
for turn in picked:                                           # ⑤ 最近窗口
    pack.messages.extend(turn.messages)
pack.messages.append(Message.user(query))                     # ⑥ 当前问题（最后！）
```

整个 `MemoryManager` 对外只有三个方法：`add_turn()` / `build(query)` / `stats()`。
**接口越窄，越容易被替换**：生产里把 `RuleSummarizer` 换成 `LLMSummarizer`、
把 `LongTermStore` 换成向量库，`build()` 一行都不用改。

## 4. 工程要点

1. **token 估算必须用真分词器。** 本章用 `estimate_tokens`（中文 1 字≈1 token）只为观察趋势。
   真上线要按厂商的分词器算，否则"刚好卡在窗口内"的请求会在某次多出 3 个 token 时 400 报错。
2. **摘要会漂移。** 反复"压缩摘要的摘要"，细节会一层层模糊掉。
   对策：关键事实走结构化存储（本章的 `Fact`），**永不进入摘要这条有损通道**。
3. **抽取要防"把问题当答案"。** 本章实测踩过这个坑：查询「我叫什么？」被规则抽成了
   `姓名=什么`。规则抽取一定要区分"用户陈述"和"用户提问"，或者让抽取只看用户消息。
4. **闸门阈值要按业务调。** 闸门太松 → 注入无关记忆（污染）；太严 → 该想起的想不起来。
   先用离线评测集调（第 10 章），不要拍脑袋。
5. **记忆是有隐私成本的。** 长期存储意味着"用户说过的话被持久化了"：
   要有过期策略（TTL）、要能删除（用户要求遗忘时必须真删）、要区分 PII。
6. **别在每轮都做完整重压缩**，那是 O(n²) 的模型调用。
   触发式压缩（超过阈值才压）或后台异步压缩才现实。
7. **常见坑：把窗口设得太大。** 窗口越大，成本越高、中间内容越容易被忽略。
   与其加到 20 轮，不如把 20 轮里的关键信息抽成事实钉住。

提示：用 `bigrams()` 做重叠度判断；连续跑 50 轮，统计摘要漏掉了哪几条。

**练习 3（核心）· 破坏护栏并观察**
