## 0. 先看问题

第 01~03 章的 Agent 是"走一步看一步"的：想一下 → 调个工具 → 看结果 → 再想。
任务一复杂，它就露出两个毛病：

- **走错方向很晚才发现**：做到第 5 步才发现前提是错的，前 4 步的钱和时间全白花；
- **没法提前检查**：等它真的动手（发短信、扣款、写文件）时，你才知道计划跑不通。

那"先一次性想好全部步骤"行不行？也不行。看本章的反面教材（`--section 1` 的真实输出）：

```text
  ℹ️  规划时（t=0）订单还是「已发货」，模型据此写出 2 步计划，并把运费 33.75 写死进去：
    │ 1. draft_reply({"order_id": "A1001", "kind": "shipped", "detail": "加急运费 33.75 元"})
    │ 2. send_reply({"order_id": "A1001", "text": "您的订单 A1001 已发货，加急运费 33.75 元。"})

  ⚠️  执行前，订单 A1001 被取消了（环境变了 —— 这在意料之外，但完全在情理之中）。

  Executor 交出的报告    : 任务已完成：已计算加急运费 33.75 元，并已通知客户订单 A1001 已发货。（执行日志里有 2 条 WARN，已忽略）
  真实发生的错误           : ["draft_reply: ValueError: 通知类型 'shipped' 与订单 A1001 的真实状态「已取消」不符（应该用 'cancelled'）", ...]
  世界里的真实副作用         : （空 —— 一条通知都没发出去）
```

两种死法，第二种比第一种危险得多：

| 死法 | 表现 | 危害 |
|---|---|---|
| ① 让异常冒出来 | 第二步报错，任务中断 | 至少你知道出事了，前一步的成果也还在 |
| ② **吞掉错误继续跑** | 交出"任务已完成"的报告 | **假成功**：报告说通知了，客户什么都没收到 |

第二种是线上事故的主要来源。根因只有一个：**计划里的每一步都是假设，而朴素执行器把假设当成了事实**。

## 1. 原理

### 1.1 三个角色，两种性质

```
         ┌──────────────────────────────────────────────────────┐
         │                    任务（自然语言）                    │
         └───────────────────────┬──────────────────────────────┘
                                 ↓
   ┌─────────────┐     步骤列表（结构化数据：id/goal/tool/args/depends_on）
   │  Planner    │  ← 模型，不确定
   └──────┬──────┘
          ↓
   ┌─────────────┐     每一步的真实结果（Observation）
   │  Executor   │  ← **纯代码，确定性，可测试**
   └──────┬──────┘
          │  某一步失败 / 依赖不满足 / 参数引用失效
          ↓
   ┌─────────────┐     修正后的步骤列表（新版本）
   │  Replanner  │  ← 模型，不确定
   └──────┬──────┘
          └────────→ 回到 Executor（带预算，不能无限循环）
```

**为什么 Executor 必须是确定性代码？**
因为可归因。计划可以错，但"按计划执行"这件事不允许有随机性 ——
否则你永远分不清失败是**计划的锅**还是**执行的锅**。

### 1.2 计划为什么必须是结构化数据

| 形态 | 能校验 | 能执行 | 能 diff | 能统计 |
|---|---|---|---|---|
| 一段自然语言（"先查订单再算运费最后通知客户"） | ✗ | ✗ | ✗ | ✗ |
| 结构化 Step 列表 | ✓ | ✓ | ✓ | ✓ |

结构化之后，一个步骤至少要有四个字段：

```python
Step(id=2, goal="用订单里的重量算出加急运费",
     tool="calc_freight",
     args={"order_id": "$1.order_id", "weight_kg": "$1.weight_kg", "speed": "加急"},
     depends_on=[1])
```

- `goal` —— 写给人看，也写给**重规划时的模型**看（它靠这句话判断哪条假设破了）；
- `tool` + `args` —— 可校验（工具存不存在、参数齐不齐）；
- `depends_on` —— 决定执行顺序，也决定失败时谁会受牵连；
- `args` 里的 `$1.weight_kg` —— 让数据**在步骤之间流动**，而不是让模型猜数字。

> `$1.weight_kg` 这种引用语法是本章最值钱的一行设计。
> 没有它，模型只能把重量"猜"出来写进参数里 —— **那就是幻觉的发源地**。

### 1.3 静态校验 vs 运行时校验

```
   计划期（便宜，能提前发现问题）        执行期（昂贵，副作用不可撤销）
   ─────────────────────────────       ──────────────────────────────
   ✓ 工具名是否存在                     ✓ 参数值是否合法（weight_kg 真是数字吗）
   ✓ 依赖是否成环                       ✓ 业务规则是否满足（订单取消了吗）
   ✓ 必填参数是否齐全                   ✓ 环境是否变化（假设还成立吗）
   ✗ 查不出"值对不对"
```

一句话：**能静态拦下的，绝不拖到执行期**；静态查不出的，执行期必须有兜底。

### 1.4 计划粒度：不是越细越好

| 粒度 | 步数 | 工具调用 | 失败后可复用 | 问题 |
|---|---|---|---|---|
| 太粗（1 步干 4 件事） | 少 | 少 | **0** | 失败时不知道是哪件事破了，也没法最小修复 |
| 合适（1 步 1 件事） | 中 | 中 | 有 | —— |
| 太细（1 字段 1 步） | 多 | 多 | 有（但没多） | 调用成本翻倍，中间结果把上下文撑爆 |

判据：**以"失败时能精确定位、且不必连累已完成的步骤"为标准**，不是越细越好。
（第 05 章会看到"把一堆中间结果塞进上下文"具体有多贵。）

## 2. 动手实现

本章有两个文件：`planner.py`（机制）与 `demo.py`（教学）。真实工程里也应该这么分 ——
**规划逻辑与教学叙事分开**，读者才不会被细节淹没。

### 2.1 执行前校验（`validate_plan`）

```python
def validate_plan(plan: Plan, tools: ToolRegistry) -> list[str]:
    problems: list[str] = []
    ...
    for s in plan.steps:
        if s.tool not in known:
            problems.append(f"第 {s.id} 步用了不存在的工具 {s.tool!r}，可用工具：{sorted(known)}")
        ...
        for d in s.depends_on:
            if d > s.id:
                problems.append(f"第 {s.id} 步依赖了后面的第 {d} 步 —— 依赖只能指向更小的步骤编号")
    return problems
```

设计决策有三条值得单独说：

1. **一次性收集全部问题**，而不是遇到第一个就返回 —— 减少和模型的来回次数；
2. **依赖只允许指向更小的编号**：这一条规则一石二鸟，既挡住"依赖不存在的步骤"，
   也天然挡住循环依赖（A 等 B、B 等 A 时，必然有一个依赖指向更大的编号）；
3. 校验在 `Executor.run()` 里**自动执行**，而不是提供给调用方"记得自己调"——
   安全机制一旦可选，就等于没有。

### 2.2 参数引用解析（`resolve_args`）

```python
_REF_EXACT_RE = re.compile(r"^\$(\d+)\.([\w\.]+)$")     # 整个参数就是一个引用
_REF_ANY_RE = re.compile(r"\$(\d+)\.([\w\.]+)")         # 字符串内插值
```

两种写法用途不同：

```python
{"weight_kg": "$1.weight_kg"}                       # → 2.5   （保留原始类型，数字还是数字）
{"detail": "运单号 $1.tracking，请查收"}              # → "运单号 SF1234567890，请查收"
```

解析失败**必须抛 `RefError` 并触发重规划**，而不是返回 `None` 让工具自己去报错 ——
因为"引用解析不了"的真实含义是：**上游结果和计划的假设不一致**，这是重新规划的信号，不是参数错误。

### 2.3 执行 + 重规划主循环

```python
while True:
    problems = validate_plan(plan, self.tools)
    if problems:                       # 跑不通的计划一步都不执行
        stop_reason = "plan_invalid"; break
    outcome = self._execute(plan)      # 逐步执行
    if outcome is None:                # 全部成功
        stop_reason = "completed"; break
    failed_step, reason = outcome
    if replans >= self.planner.max_replans:   # ★ 预算，必需品
        stop_reason = "replan_exhausted"; break
    new_plan = self.planner.replan(task, plan, failed_step, reason)
    reused += self._carry_over(plan, new_plan)  # ★ 复用已完成的步骤
    plans.append(new_plan); plan = new_plan
```

三个 `break` 对应三种停机原因：`plan_invalid` / `completed` / `replan_exhausted`。
**每个循环都必须能证明自己会停** —— 这是第 01 章 `max_steps` 的同一条道理。

### 2.4 重规划要复用，不要重跑（`_carry_over`）

```python
def _carry_over(self, old: Plan, new: Plan) -> int:
    reusable = old.done_signatures          # {工具+参数指纹: 已成功的步骤}
    reused = 0
    for step in new.steps:
        prior = reusable.get(step.signature)
        if prior is not None:
            step.status, step.result, step.observation = "done", prior.result, prior.observation
            reused += 1
    return reused
```

这 10 行是"重规划能不能省钱"的分水岭：

- 没有它，重规划 = **从头再跑一遍**：重复的读操作浪费钱，重复的写操作是**事故**
  （客户收到两条短信、账户被扣两次钱）；
- 有它，只有"指纹相同且已成功"的步骤会被沿用。

### 2.5 重规划提示词必须有三块

```python
prompt = (
    f"# 任务\n{task}\n\n"                       # ① 原始任务（防止越跑越偏）
    f"# 可用工具\n{self._tool_manual()}\n\n"
    "# 重规划\n"
    f"上一版计划在执行中失败了，这是它现在的真实状态：\n{history}\n\n"   # ② 已完成的真实结果
    f"# 失败点\n第 {failed.id} 步《{failed.goal}》失败。\n原因：{reason}\n\n"  # ③ 失败原因
    "# 要求\n1. 不要重复执行已经成功的步骤……"
)
```

只给模型一句"失败了，重新规划吧"是没用的：它不知道**哪条假设错了**，
只会把同一份计划再写一遍 —— 这是重规划最常见的失败形态。

## 4. 工程要点

1. **计划是缓存，不是承诺。** 任何"计划时拿到的事实"在执行时都可能过期。
   凡是有副作用的步骤（发送、支付、写入），执行前都要**再校验一次前置条件** ——
   本章 `send_reply` 里那句"订单已取消但文案声称已发货 → 拒绝发送"就是这层兜底。
2. **重规划要带上原始任务。** 不带的话，重规划两三次后模型会忘记最初要干什么，
   开始优化一个自己发明出来的目标。
3. **重规划必须有预算**（`max_replans`）。模型可能反复给出跑不通的计划，
   没有预算就是无限烧钱 —— 和 `max_steps` 是同一类保护。
4. **幂等性决定重规划的安全边界。** 读操作可以随便重跑，写操作必须靠幂等键
   （第 13 章）才能安全重试。没有幂等保证时，"复用已完成步骤"就不是优化，而是**必需**。
5. **不要迷信静态校验。** 它只查结构，不查语义。`weight_kg=250`（把克当千克）
   静态完全合法，只有业务规则和范围校验拦得住（第 02 章的 JSON Schema `minimum/maximum`）。
6. **步数是账单上的乘数。** 每一步至少一次模型调用或工具调用；细粒度计划看着"严谨"，
   实际是把延迟和成本乘以 2。
7. **常见坑：让模型直接输出"计划"而不校验工具名** —— 幻觉工具（`search_web`）在规划阶段
   比在 ReAct 阶段更常见，因为规划时模型还没看到任何真实反馈。

观察 `CyclicPlanLLM` 那份"1 等 2、2 等 1"的计划会发生什么。
提示：`Executor._execute()` 会把第 1 步标成 `blocked`（依赖未满足），然后触发重规划，
再被同一份计划卡住 —— 最终靠 `max_replans` 兜底。**这就是"没有静态校验时，你只能靠预算兜底"**。
把结论写进 `NOTES.md`。
