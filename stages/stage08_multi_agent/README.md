> 一句话本质：多智能体 = `角色分工` + `消息传递` + `结果仲裁`。
> 收益来自**专业化与隔离**，代价是**通信开销与不可控性**。
> 先说结论：**多智能体不是自动更好** —— 一个 Agent 能干的事，别上三个。

## 0. 先看问题

一张真实的客服工单：

```
工单 T-2025-0117：李先生投诉「说好 1 月 5 日送到，现在还没到，我要赔付！」
订单 A1001：已发货 / 顺丰 SF1234567890 / 承诺 2025-01-05 / 实际 2025-01-06 到达（延迟 24 小时）
赔付条款：
  A-1  待付款或已取消                        → 无需赔付
  A-2  已发货且超承诺日 72 小时、无物流轨迹   → 现金赔付 50 元
  B-2  已发货且轨迹正常、延迟 ≤ 48 小时       → 不现金赔付；补偿 20 元运费券
```

正确答案显然是 **B-2：补 20 元运费券**（延迟 24 小时 ≤ 48 小时，且轨迹正常）。

但让"一个 Agent 什么都干"的版本上，它给出的是：

```
【工单 T-2025-0117 回复】李先生您好，非常抱歉。经核实订单 A1001 存在延误，
按赔付规则我们将在 3 个工作日内现金赔付 50 元。（内部备注：该承运商本月已有 3 起同类延误（内部数据，勿外传））
```

四个问题：

1. 记错了条款 —— 记住了"延误赔 50 元"这条醒目的规则，漏掉了 B-2 的例外；
2. 没有引用条款编号，处理依据不可溯源；
3. **把内部备注写进了给客户的话术**（数据外泄事故）；
4. 顺序不可控：这次先查订单再道歉，下次可能反过来。

失败原因不是模型笨，而是**数据、条款、话术全挤在一个上下文里**，注意力被摊薄了。

于是我们很自然地想：**能不能让懂条款的人专门管条款？**

于是就有了多智能体 —— 但也要先看清它的账单。

## 1. 原理

### 1.1 三种协作形态

```
① 单 Agent 一把梭（本章的基线）
   ┌────────────────────────────────┐
   │  订单数据 + 条款 + 话术规范     │──▶ 1 次调用 ──▶ 回复
   └────────────────────────────────┘
   便宜，但注意力摊薄 → 专业判断容易错

② 共享上下文 + 自由讨论（反面教材）
   ┌──────────────────────────────────────────────┐
   │  一块共享草稿纸：所有人往上写，所有人读全部    │
   │  数据专家 ↔ 政策专家 ↔ 文案专家 ↔ ……          │
   └──────────────────────────────────────────────┘
   贵（上下文随轮次膨胀），而且会**互相污染**

③ 主管 + 隔离专家（本章的正解）
              ┌────────────┐
              │  Supervisor │  只做：分解 / 分派 / 仲裁
              └──┬───┬───┬──┘
        ┌────────┘   │   └────────┐
        ▼            ▼            ▼
   ┌─────────┐  ┌─────────┐  ┌─────────┐
   │ 数据专家 │  │ 政策专家 │  │ 文案专家 │   各自独立的上下文
   │ 订单数据 │  │ 条款表   │  │ 话术规范 │   互不可见
   └─────────┘  └─────────┘  └─────────┘
        └────────────┴────────────┘
              只传「结论」，不传「上下文」
```

### 1.2 隔离到底隔离了什么

| | 数据专家 | 政策专家 | 文案专家 |
|---|---|---|---|
| 系统提示词 | 查数据的方法 | 条款表 | 话术规范 |
| 收到的输入 | 主管给的子任务 | **结构化事实**（不含内部备注） | **仲裁结论**（不含条款表） |
| 上下文规模 | 72 字符 | 227 字符 | 168 字符 |
| 能不能看到内部备注 | 能 | **不能** | **不能** |

关键机制是**汇报结构化**：专家交回来的不是一个字符串，而是一个带字段的对象。

```python
@dataclass
class WorkerReport:
    worker: str
    conclusion: str                 # 一句话结论
    facts: dict[str, str] = field(default_factory=dict)
    evidence: str = ""              # 依据（例如条款编号）
    needs_help: bool = False        # 踢皮球信号：我干不了，需要别人补材料
    prompt_chars: int = 0           # 这次它看了多少字（成本可观测）
```

有了 `facts` 字典，主管转发时就能**只挑需要的字段**：

```python
# 交给政策专家的是 facts（结构化），而不是数据专家的原始输出
facts_text = "\n".join(f"- {k}：{v}" for k, v in data_report.facts.items())   # 内部备注不在里面
```

> **传「结论」，不传「上下文」** —— 这一条是多智能体能不能省钱、能不能不互相污染的**分水岭**。

### 1.3 收益与代价

| | 单 Agent | 共享讨论 | 主管 + 隔离专家 |
|---|---|---|---|
| 模型调用 | 1 | 6（3 人 × 2 轮） | 3 |
| 提示词总字符 | 361 | 1809 | 464 |
| 结论正确性 | ❌ 漏条款例外 | ❌ 被草稿污染 | ✅ 引用 B-2 |
| 数据外泄 | ❌ 内部备注外发 | ❌ 内部备注外发 | ✅ 无 |
| 可审计性 | 无 | 有记录但噪音大 | 每条消息可溯源 |
| 可替换性 | 牵一发动全身 | 无边界 | 换掉政策专家即可 |

**多智能体买到的**：专业化（各管一摊，注意力不被摊薄）+ 隔离（各看一份，不互相污染）+ 可审计（消息留痕）。
**多智能体付出的**：N 倍调用 + 一个新的失败模式（踢皮球 / 死锁 / 谁说了算）。

### 1.4 三个必须回答的工程问题

1. **谁来决定下一个发言人？** —— 本章是主管（集中式调度）。
   去中心化（谁都能 @ 谁）看起来更"智能"，但你会立刻失去可控性和可审计性。
2. **专家之间怎么不互相污染？** —— 上下文隔离 + 结构化汇报 + 总线上只跑结论。
3. **讨论什么时候停？** —— `max_rounds`。没有它，多智能体就是一张会自动续费的账单。

## 2. 动手实现

代码在 `stages/stage08_multi_agent/demo.py`，全部离线可跑。

### 2.1 消息总线：只投递、只记账

```python
@dataclass(frozen=True)
class Envelope:
    sender: str
    recipient: str
    topic: str          # task / result / question / arbitration
    payload: str
    round: int = 1

class MessageBus:
    """只负责投递与记账，**不做任何智能**。"""
    def __init__(self) -> None:
        self.log: list[Envelope] = []

    def send(self, env: Envelope) -> Envelope:
        self.log.append(env)
        return env
```

为什么第一天就要有总线？因为**多智能体最难查的 bug 就是"谁把什么告诉了谁"**。
有了它，"主管有没有把内部备注转发出去"这种问题是一行断言的事：

```python
results.append(check_that(
    "隔离：政策专家只拿到结构化事实（不含内部备注）",
    "内部备注" not in policy_ctx and "延迟小时数" in policy_ctx, ...))
```

### 2.2 专家：上下文入口只有一个

```python
class Worker:
    def handle(self, instruction: str) -> WorkerReport:
        # ★ 只有两块：自己的岗位说明书 + 主管给的子任务
        messages = [Message.system(self.system_prompt), Message.user(instruction)]
        self.contexts.append("\n".join(m.content for m in messages))   # 记录"我看到了什么"
        resp = self.llm.complete(messages)
        self.outputs.append(resp.text)                                 # 记录"我说了什么"
        report = self.parse(resp.text)
        report.prompt_chars = sum(len(m.content) for m in messages)
        return report
```

**这个函数只有 8 行，但它是整章的支点**：专家拿不到总线上的历史、拿不到别的专家说过的话、
也拿不到用户的原始长对话。隔离不是靠"提示词里叮嘱它别看"，而是靠**结构上根本拿不到**。

### 2.3 主管：分解 → 分派 → 仲裁

```python
def run(self, ticket: Ticket) -> SupervisorResult:
    # ① 分派给数据专家（无依赖）
    reports["data"] = self.workers["data"].handle(...)
    # ② 分派给政策专家：只传它需要的事实
    reports["policy"] = self._ask_policy(reports["data"], rounds)
    # ③ 踢皮球保护：互相要材料时主管转达，但有轮数上限
    while reports["policy"].needs_help or reports["data"].needs_help:
        if rounds >= self.max_rounds:
            stop_reason = "round_limit"
            self.bus.send(Envelope("supervisor", "arbiter", "arbitration", "达到轮数上限，强制结束讨论。"))
            break
        ...
    # ④ 仲裁（确定性规则，不是模型调用）
    decision, final_reply = self.arbitrate(reports)
```

仲裁**必须是确定性的 if/else**：

```python
def arbitrate(self, reports) -> tuple[str, str]:
    policy, data = reports.get("policy"), reports.get("data")
    if data is None or data.needs_help:
        return "转人工：事实缺失", HOLD_REPLY
    if policy is None or policy.needs_help or not policy.evidence:
        return "转人工：条款依据缺失（专家未达成一致）", HOLD_REPLY
    if policy.evidence not in POLICY_BY_ID:
        return f"转人工：依据 {policy.evidence} 不可溯源", HOLD_REPLY
    rule = POLICY_BY_ID[policy.evidence]
    return f"依据条款 {rule.code}：{rule.action}", ""
```

注意 **"拿不到可溯源依据就转人工"** 这条兜底：宁可给客户一句"我们正在核实"，
也不要猜一个赔付结论出去。这是多智能体最后的体面。

### 2.4 反面教材：共享上下文为什么更贵更糟

```python
def run_shared_context(ticket, rounds=2):
    transcript = [
        Message.system(SHARED_SYSTEM),
        Message.user(f"工单 {ticket.ticket_id}：{ticket.complaint}"),
        Message.assistant("[早期草稿] 结论：按 A-2 现金赔付 50 元。（待确认）"),   # ← 污染源
    ]
    for r in range(1, rounds + 1):
        for speaker in ("数据专家", "政策专家", "文案专家"):
            transcript.append(Message.user(f"第 {r} 轮，请 {speaker} 发言。"))
            sizes.append(sum(len(m.content) for m in transcript))   # 它这次读了多少字
            resp = llm.complete(transcript)                          # ← 看到的是全部历史
            transcript.append(Message.assistant(resp.text))
```

每次调用要重读全部历史 → 上下文 122 / 205 / 249 / 341 / 424 / 468 字符，一路膨胀；
更糟的是那条"早期草稿"变成了所有人的共识：

- 政策专家不再查条款，直接附和："同意草稿的判断，本单应现金赔付 50 元。"
- 文案专家照抄内部备注进对客回复。

> **共享的不是「记忆」，是「偏见」：谁先说话，谁就定义了讨论的起点。**

## 4. 工程要点

**① 先试单 Agent。** 这一章最容易被误读成"多智能体很厉害"。事实相反：
本章的对比表里，单 Agent 只用了 1 次调用。只有当子任务**需要不同的知识**、
而且这些知识**能被切干净**时，分工才划算。两个专家看同一份资料 = 同一个 Agent 的两次调用。

**② 隔离是结构问题，不是提示词问题。**
"我在提示词里写了不要透露内部信息" 不是隔离。隔离是**专家在结构上拿不到那些信息**：
`handle()` 只接收 `(system_prompt, instruction)` 两块。

**③ 汇报要结构化，转发要挑字段。**
一段自由文本里什么都有（包括不该外传的内部备注）。`WorkerReport.facts` 让你能只传需要的字段 ——
这既省 token，又是数据安全的边界。

**④ 仲裁必须是确定性的。**
"谁权威、冲突听谁的、缺依据怎么办" 是流程规则，不是判断题。把仲裁交给模型，
等于把系统的控制流交给概率。本章的仲裁是 6 行 if/else，0 次模型调用。

**⑤ 上限不是可选项。**
本章的踢皮球场景：两个专家互相要材料，一共产生了 13 条消息。如果没有 `max_rounds`，
它们会一直要下去。**上限之外还要有触顶后的行为** —— 本章是"转人工 + 保守话术"，
绝不是"随便编一个结论"。

**⑥ 触顶后不要把失败藏起来。**
`stop_reason="round_limit"` + `decision="转人工：事实缺失"`，上层能立刻看懂发生了什么。
把失败包装成"已完成"，是多智能体系统里最贵的 bug。

**⑦ 上下文格式决定专家正确率。**
本章开发过程中真实踩到的坑：主管一开始把事实拼成一句话 `轨迹正常`，
政策专家解析不出来，直接判成了 A-1（无需赔付）。改成结构化字段 `- 轨迹：正常` 后立刻正确。
**专家"看起来变笨了"，十有八九是上游交接格式的问题**，不是模型的问题。

**⑧ 常见误区**

| 误区 | 现实 |
|---|---|
| "多智能体一定比单 Agent 强" | 通信开销 + 不确定性可能让效果更差 |
| "人多力量大，多放几个专家" | 每多一个角色 = 多一份调用 + 多一个失败点 |
| "让它们自由讨论更聪明" | 共享上下文 = 传播偏见 + 成本平方级增长 |
| "让模型来当裁判" | 裁判必须是确定的规则，否则每个工单结论都不一样 |
| "反正有重试，不怕踢皮球" | 重试会把账单放大，不解决"谁说了算" |
